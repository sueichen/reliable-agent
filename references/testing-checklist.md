# 测试检查清单

> 用于 `/build-reliable` 的 TDD 循环和 `/request-review-reliable` 的测试审查。

## 测试金字塔

```
       /\
      /E2E\       5% — 关键用户流程
     /------\
    / 集成测试 \   15% — 模块间交互
   /----------\
  /  单元测试    \  80% — 公共接口纯逻辑
 /--------------\
```

## TDD 循环（Red-Green-Refactor）

### RED 阶段
- [ ] 测试描述行为（behavior），不描述实现（implementation）
- [ ] 测试通过公共接口调用
- [ ] 测试名读起来像规格说明
- [ ] 运行测试 —— 确认失败（证明它检测到了缺失的行为）
- [ ] 如果测试在没有实现的情况下通过，重新思考测试

### GREEN 阶段
- [ ] 最小实现使测试通过
- [ ] 无投机性功能（"以后可能用到"）
- [ ] 实现不超过 ~50 行（在测试通过之前）
- [ ] 运行测试 —— 确认通过

### Verify 阶段
- [ ] 运行完整测试套件
- [ ] 确认无回归
- [ ] 运行构建确认

### REFACTOR 阶段
- [ ] 仅在 GREEN 时重构（绝不在 RED 时重构）
- [ ] 提取出现 >= 2 次的重复
- [ ] 深化模块：将复杂性移到简单接口背后
- [ ] 每次重构后运行测试
- [ ] 测试破坏 → 撤销重构

## 测试反模式

| 反模式 | 为什么是问题 |
|--------|------------|
| **测试实现而非行为** | 重构时测试破坏但行为未变 |
| **Mock 内部协作者** | 测试耦合到内部结构 |
| **无审查的 Snapshot 测试** | Snapshot 漂移隐藏回归 |
| **无断言的测试** | 永不失败的测试 = 无用 |
| **依赖共享可变状态的测试** | 执行顺序依赖的失败 |
| **水平切片** | 预先写所有测试 = 想象的测试，非现实的 |
| **测试之间相互依赖** | 不能独立运行，难以定位失败 |

## 覆盖维度

对于每个变更的组件：

| 维度 | 检查 |
|------|------|
| 正常路径 | 正常使用场景是否测试？ |
| 边界情况 | null, empty, zero, 边界值, 最大长度？ |
| 错误路径 | 无效输入, 网络失败, 超时, 部分成功？ |
| 并发 | 竞态条件, 快速重复调用, 乱序响应？ |
| 状态转换 | 所有有效转换覆盖？无效转换拒绝？ |
| 回归 | 此区域的以前修复过的 bug 有测试吗？ |

## Beyonce Rule

> "If you liked it then you should have put a test on it."

所有非平凡行为必须有测试。代码合并前测试必须通过。如果某行为重要到值得编写，它就重要到值得测试。

## Prove-It 模式（Bug 修复）

1. 写一个复现 bug 的测试 → 确认测试失败
2. 实现修复
3. 确认测试通过
4. 确认无回归
