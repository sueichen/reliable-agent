# 性能优化典型案例

> 精选典型优化案例，覆盖不同维度组合，含 before/after 数据

---

## 案例 1: 数组访问顺序（内存维度）

**场景**: C 图像处理程序，按列遍历二维数组
**现象**: 处理 400 万像素耗时 545ms
**诊断**: perf stat 显示高 cache-miss 率

**根因**: 列访问破坏了空间局部性
```c
// 优化前: 按列访问
for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
        c[i][j] = a[i][j] + b[j][i];  // b[j][i] 跨大步
```

**优化**: 按行访问
```c
// 优化后: 按行访问
for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
        c[i][j] = a[i][j] + b[i][j];
```

**收益**: 545ms → 236ms（2.3x）
**教训**: 先检查数据访问模式再怀疑算法

## 案例 2: 伪共享修复（多线程 + 内存维度）

**场景**: 多线程计数器，4 线程反而比单线程慢
**现象**: perf c2c 显示高 HITM 计数
**诊断**: 两个线程修改变量落在同一 Cache Line

```c
// 优化前: x 和 y 在同一 Cache Line
struct foo { int x; int y; } f, testf;
// 线程 A: f.x 频繁读, 线程 B: f.y 频繁写 → 互相失效
```

**优化**: Cache Line 对齐
```c
struct foo {
    int x;
    char padx[124];  // 鲲鹏 Cache Line 128B
    int y;
    char pady[124];
};
```

**收益**: 鲲鹏 920 上耗时从 2.955s → 2.248s（1.31x）
**教训**: 多线程场景必须考虑 Cache Line 边界

## 案例 3: 结构体重排（内存维度）

**场景**: 大量结构体对象，sizeof 较大，内存占用超预期
**诊断**: 成员未按对齐要求排列，padding 占 1/3 空间

```c
// 优化前: sizeof = 24
struct Test1 { char a; double b; int c; short d; };
// 内存布局: [a][7B padding][b 8B][c][d][2B padding]

// 优化后: sizeof = 16
struct Test2 { double b; int c; short d; char a; };
// 内存布局: [b 8B][c][d][a][1B padding]
```

**收益**: 内存节约 33%，Cache 命中率提升
**教训**: 结构体成员按对齐要求降序排列

## 案例 4: KML 加速库替换（CPU 维度）

**场景**: HPC 软件 CP2K 运行在鲲鹏平台
**诊断**: `perf record` 热点分析发现 `dgemm` 函数占比 79.91%
**根因**: 通用 BLAS 库未针对鲲鹏优化

**优化**: 替换为 KML（鲲鹏数学库）
```bash
# 链接 KML_BLAS
LIBS += $(MATHLIB_PATH)/libkblas_armv8ss_v1.2.0.a
```

**收益**: 1601.49s → 433.58s（3.69x，加速 72.93%）
**教训**: 热点函数优先检查是否有平台优化库

## 案例 5: PGO 优化（CPU 维度）

**场景**: C++ 编译型服务，关键路径有大量分支
**诊断**: perf 显示分支预测失败率 > 3%
**根因**: 编译器无法静态推断分支走向

**优化**: PGO 两轮编译
```bash
gcc -O2 -fprofile-generate prog.c -o prog
./prog < representative_input   # 收集运行数据
gcc -O2 -fprofile-use prog.c -o prog  # 反馈优化
```

**典型收益**: 5%~15%，极端场景（分支密集）可达 30%
**教训**: 分支密集的代码，PGO 是最低成本的优化

## 通用教训

1. **先观测再优化** — 所有案例都始于 perf/iostat 数据，而非直觉
2. **热点驱动** — dgemm 占 80% 时间，优化它比优化其他所有加起来更有效
3. **平台差异重要** — 鲲鹏 Cache Line 128B vs x86 64B，迁移时需重新验证
4. **编译器+库优先** — PGO、KML 等无需改业务代码，风险低收益高
5. **数据布局 > 算法** — 前三个案例都是数据布局问题，改算法之前先看布局
6. **一次优化一个维度** — 并发+Cache 问题有交互效应，先隔离再修
