# Grill-Me 对抗式提问执行指南

> 本文件是 ra-plan 技能 Step 3 (Grill-Me) 的详细执行规范。
> 由 `ra-plan/SKILL.md` 在 Step 1 加载上下文中引用。
>
> 目标：通过逐轮、交互式的对抗提问，压力测试需求的完整性。

---

## 1. Grill 维度定义

每个维度在下表中定义。根据需求复杂度选择相关维度，跳过不相关的维度并记录理由。

| 维度 | 触发条件 | 何时可跳过 | 示例问题方向 |
|------|---------|-----------|-------------|
| **边界情况** | 需求涉及输入/输出/状态变化 | 需求纯文档或配置变更 | null/empty/零值/超大输入/并发/超时 |
| **失败模式** | 需求涉及网络/IO/外部依赖 | 纯计算/纯内存操作 | 网络断/超时/部分成功/数据损坏/重试风暴 |
| **一致性** | 需求与已有系统有交互 | 全新独立系统 | 与已有代码矛盾？与 CLAUDE.md 约束冲突？ |
| **范围** | 所有需求 | 从不跳过 | 明确"不构建什么"——防止范围蔓延 |
| **安全** | 需求涉及用户输入/权限/数据/认证/授权/序列化/配置/依赖 | 纯文档格式变更 | 新攻击面？权限提升？数据泄露？注入向量？依赖风险？ |
| **性能** | 需求涉及数据处理/网络/存储 | 单次执行/非关键路径 | 预期负载下瓶颈？N+1 查询？内存占用？ |

### 1.1 维度选取规则

1. **范围**维度从不跳过
2. 其余维度根据需求信号判断：
   - 需求涉及 ≥3 个文件 → 至少覆盖边界、一致性
   - 需求涉及网络/IO → 必须覆盖失败模式
   - 需求涉及用户输入/认证/授权/数据存储/序列化/依赖更新/配置管理 → 必须覆盖安全
   - 需求涉及循环/批量处理 → 必须覆盖性能
3. 跳过的维度必须在 plan 文件的 "Grill-Me 记录" 章节中注明理由

## 2. 候选选项生成规则

### 2.1 方向互斥检查

每个问题的候选选项必须代表**根本不同的方向**，而非同一方向的不同实现：

* [PASS] "A) 乐观锁 B) 悲观锁 C) 不处理并发" — 三个根本不同的方向
* [FAIL] "A) Redis 缓存 B) Memcached 缓存 C) 本地缓存" — 同一方向（都缓存），只是实现不同

**自检清单（生成选项后、展示前执行）：**
1. 如果有两个选项可以用"本质上都是 X"来描述 → 合并它们
2. 如果所有选项都假设"必须做 X" → 增加一个"不做 X"的选项
3. 选项数量：2-4 个（少于 2 → 不是真正的选择；多于 4 → 认知负担过高）

### 2.2 最小化/放弃选项

每个问题**必须**包含至少一个最小化或放弃选项：

* "不处理这个情况，接受风险"
* "推迟到下一版本"
* "用最简单的手动方案，不做自动化"
* "放弃这个需求，因为……"

这个选项迫使思考"我们真的需要做这个吗？"，防止过度设计。

## 3. 动态轮数逻辑

### 3.1 复杂度估算

| 信号 | 权重 |
|------|------|
| 涉及文件数 ≥ 5 | +2 维度 |
| 新模块/新服务 | +1 维度 |
| 修改已有公共接口 | +1 维度 |
| 涉及安全/权限 | +1 维度 |
| 涉及性能敏感路径 | +1 维度 |
| 需求描述 < 50 字 | +1 维度（信息不足，需更多澄清） |

**复杂度映射：**
* 0-1 个信号 → 简单需求 → 2-3 轮（覆盖范围 + 1-2 个相关维度）
* 2-3 个信号 → 中等需求 → 4-5 轮（覆盖范围 + 3-4 个相关维度）
* 4+ 个信号 → 复杂需求 → 6-12 轮（覆盖所有相关维度，每个维度至多 2 轮，总计 ≤ 12 轮硬上限）

### 3.2 终止条件

满足以下任一条件时 grill-me 终止：
1. 所有相关维度已覆盖
2. 连续 3 轮用户回答均未产生新的设计决策（例如用户连续 3 轮回答"随便"、"都行"、或机械重复前一轮答案而无新增信息）
3. 用户明确表示"grill-me 可以结束了"

## 4. 敷衍回答处理

### 4.1 什么是敷衍回答

以下模式的用户回答视为敷衍（仅适用于文本降级模式下的自由文本回复；通过 AskUserQuestion 工具提交的选项选择始终视为实质性回答）：
* "随便" / "你定吧" / "都行" / "都可以"
* "不知道" / "不清楚"（无后续提问）
* 直接回复选项字母但无任何解释或思考（**仅文本降级模式**）
* 明显与问题无关的回答

### 4.2 处理策略

**当检测到敷衍回答时：LLM 自主选择最佳方案并继续执行。**

**例外：安全维度** — 当维度为"安全"时，敷衍回答不可被自主处理。必须追问用户，明确标注："这是一个安全相关决策，需要你明确选择。" 用户连续 2 次敷衍安全问题时，选择最保守的安全方案（而非"接受风险"），并在 plan 中记录"安全决策由 LLM 保守选择"。

自主选择规则：
1. 如果有一个选项明显更适合当前需求的上下文 → 选择它
2. 如果有推荐选项（标注了"推荐"） → 选择推荐项
3. 如果无法判断 → 选择最保守/最小化的选项
4. **不要追问用户** — 直接决策推进（安全维度除外）
5. **不要在 plan 文件中标注该回答为"敷衍"** — 正常记录即可

## 5. 平台适配

### 5.1 AskUserQuestion 优先

在支持 `AskUserQuestion` 工具的平台（Claude Code），使用该工具进行 grill-me 提问：

* 每个问题一个 `AskUserQuestion` 调用
* `multiSelect: false`（单选问题）
* 选项包含 `label` 和 `description`
* 推荐选项标注 "(Recommended)"

### 5.2 降级模式

当平台不支持 `AskUserQuestion` 工具时，使用纯文本提问：

**降级模板：**
```markdown
## Grill-Me — 第 N 个问题

**问题 N：[维度] — [具体问题]**

[候选选项 A/B/C 含描述]

[等待用户回答 — 不要继续]
```

关键规则：
* 必须在提问末尾包含 `[等待用户回答 — 不要继续]` 标记
* 不要在同一个响应中写任何回答或后续内容
* 用户可以回答选项字母或自定义内容

## 6. 记录格式

Grill-me 的每轮问答必须记录在 plan 文件中。格式如下：

```markdown
## Grill-Me 决策记录

| # | 问题 | 用户选择 |
|---|------|---------|
| 1 | [维度] — [问题摘要] | **用户选择** — [简述] |
| 2 | [维度] — [问题摘要] | **用户选择** — [简述] |
| ... | ... | ... |

### 跳过的维度

| 维度 | 跳过理由 |
|------|---------|
| [维度名] | [为什么这个维度与当前需求无关] |
```

记录时机：每轮 grill-me 结束后立即追加到 plan 文件。
